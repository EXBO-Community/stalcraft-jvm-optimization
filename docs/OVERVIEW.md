# Техническая информация

## Архитектура

Проект состоит из двух бинарников, которые должны лежать в одной директории:

- `cli.exe` — пользовательский интерфейс. Интерактивное меню, установка и удаление IFEO перехвата, проверка статуса, управление конфигами.
- `service.exe` — тихий перехватчик. Регистрируется в IFEO как `Debugger` для `stalzone.exe` / `stalzonew.exe` и запускается Windows автоматически при старте игры. Не имеет UI.

При установке `cli.exe` прописывает в реестр путь именно к `service.exe`. Разделение сделано чтобы путь Windows → игра проходил через минимальный бинарник без UI-зависимостей, а всё управление оставалось в отдельном `cli.exe`.

## Механизм работы

Враппер использует механизм IFEO (Image File Execution Options) для перехвата запуска игры.
Когда запускается `stalzone.exe` / `stalzonew.exe`, Windows вместо самой игры стартует `service.exe`, передавая ему исходные аргументы лаунчера. Дальнейшее поведение `service.exe`:

1. Загружает активный конфигурационный файл из каталога `configs/` рядом с exe; при `ActiveConfig=<none>` профиль не загружается и не генерируется.
2. Валидирует независимые tunnel override для игровых регионов из `overrides.json` без сетевых запросов.
3. При включенной оптимизации заменяет конфликтующие JVM-флаги профилем. В режиме без оптимизации сохраняет параметры лаунчера, заменяя только выбранные `-Droxy_address_override.<region>`.
4. Создаёт процесс напрямую через `ntdll!NtCreateUserProcess` с атрибутом `PS_ATTRIBUTE_IFEO_SKIP_DEBUGGER`, чтобы избежать повторного перехвата через IFEO.
5. Завершается после того, как у игрового процесса появится первое видимое окно.

## Переопределение туннеля

Каталоги Roxy запрашиваются по HTTPS только при открытии соответствующего региона в TUI. Основной адрес и зеркала используются последовательно как fallback; к каждому запросу добавляется `login=EXBO-Community`.

Для измерения `cli.exe` отправляет на `tunnel_port + 1` случайный 16-байтовый UUID. Ответ должен иметь формат `UUID[16] | tunnelToBackendRtt:i32 (big-endian) | limitReached:u8`. RTT клиента измеряется локально. Одновременно выполняется не более восьми сетевых проб; срок каждой — одна секунда после допуска к этому лимиту. Ожидание в очереди в этот срок не входит. Принимаются только ответы с UUID текущего запроса и идентификатором текущего раунда; повторный запуск отменяет предыдущий раунд. При открытии группы проверяются ее узлы, а ответы показываются по мере поступления. Фоновых повторных раундов нет: свежие измерения запускаются только при повторном открытии или явном выборе `Измерить снова`.

Настройки находятся в `overrides.json`, отдельно от версионных JVM-профилей. Override для RU, EU, NA, SEA и NEA сохраняются независимо и могут действовать одновременно; `Выбор игры` очищает только текущий регион. Кэш `cache/tunnel_stats.json` хранит до 20 измерений на endpoint, состояние последнего connection limit и время его проверки; записи старше 24 часов удаляются. Узлы, которые в прошлый раз сообщили лимит, проверяются первыми и остаются недоступными для нового выбора до ответа `limitReached=false`.

Каждый поиск собирает свежую серию из 10 проб для каждого endpoint вне исключенных групп, с интервалом 100 мс между пробами одного endpoint. Обновление заменяет эти серии, а не добавляет образцы из предыдущего поиска. Большое число узлов и узлы без ответа могут увеличивать время поиска: пробы делят общий лимит параллельности, а неудачные пробы могут занимать весь отведенный срок. История используется только справочно и не входит в оценку поиска.

Поиск сохраняет все отсортированные результаты. Одновременно видны пять строк кандидатов; остальные доступны прокруткой стрелками, а в низком терминале окно уменьшается. Результаты явно помечаются как предварительные, пока хотя бы одна серия не завершена или у кандидата меньше пяти успешных ответов. `Выбрать лучший` недоступно до завершения всех серий и не выбирает автоматически кандидата с менее чем пятью успешными ответами. Такой узел можно выбрать вручную, видя число неудачных проб и образцов. Для любого выбора нужен свежий успешный ответ без лимита подключений.

Для каждой успешной пробы выбранный режим определяет значение задержки: RTT клиента + RTT сервера для суммарного RTT; только RTT клиента для клиентского режима; только RTT сервера для серверного; либо RTT клиента × вес клиента из backend + RTT сервера для режима с весом backend. Медиана и P90 вычисляются по этим значениям отдельных проб, а не по отдельным средним компонентов. При `f = число неудачных проб / число выполненных проб` оценка равна:

`медиана + 0.5 × (P90 − медиана) + ProbeTimeout_ms × f`

Режим стабильности вместо этого отдает приоритет верхней части распределения суммарного RTT:

`P90(RTT клиента + RTT сервера) + ProbeTimeout_ms × f`

`ProbeTimeout_ms` равен 1000. Чем ниже оценка, тем выше место. Неудачные пробы входят в штраф, но не в распределение задержек успешных проб. В деталях показаны медиана и P90 суммарного RTT текущей серии, процент неудачных проб, число успешных/выполненных проб и последние успешные сырые RTT клиента, сервера и их сумма. Оценка — величина для сравнения, а не измеренный пинг игры; процент неудачных проб не является потерями игровых пакетов. Малое число ответов не доказывает статистическую уверенность.

Также показан максимум серии: единственный огромный ответ остается видимым, даже если он не влияет на медиану или P90.

**Источник RTT:** серверный RTT — знаковое значение в миллисекундах из ответа туннеля, а не второе измерение этого ПК. Большие неотрицательные значения сохраняются без произвольного ограничения; устойчивая оценка не переписывает сырые RTT. Средние арифметические по истории могут оставаться высокими после большого ответа, но предыдущие раунды не влияют на оценку свежего поиска. Принятые ответы записываются как `tunnel probe reply`: регион, группа, имя узла, раунд, значения RTT и состояние лимита; UUID и сырые пакеты не записываются. Такая диагностика устанавливает источник показанного числа, но не доказывает корректность RTT до backend, сообщенного самим туннелем.

Очень короткий локальный RTT может отображаться как ноль из-за точности системных часов. Это не означает нулевую физическую задержку; измеренное значение не подменяется искусственным минимумом.

## Логирование

Оба бинарника пишут структурированные логи в файл `logs/wrapper.log` рядом с exe: запуск, детект железа, загрузка конфига, старт игрового процесса, exit code. Путь пользователя редактируется, сырые аргументы лаунчера и JVM-флаги не пишутся. Файл усечётся при превышении 2 MB.

Отдельного JVM/GC лога нет — STALZONE использует кастомную сборку OpenJDK 9 без поддержки `-Xlog` и `-Xloggc` в CLI, поэтому направить unified logging в файл невозможно. Для большинства проблем достаточно `wrapper.log`.

## Взаимодействие через CLI

Установка перехвата IFEO

```bash
cli.exe install       # установить перехват IFEO
```

Проверка статуса перехвата

```bash
cli.exe status        # проверить статус перехвата
```

Удаление перехвата IFEO

```bash
cli.exe uninstall     # удалить перехват IFEO
```

Управление конфигами

```bash
cli.exe config list
cli.exe config releases
cli.exe config regenerate v1.1.2
cli.exe config select v1.1.2/default
cli.exe config disable
```

Запуск `cli.exe` без аргументов открывает интерактивное меню с теми же действиями и управлением конфигами.

## Сборка проекта

`cli.exe` и `service.exe` можно не только скачать из релизов, но и собрать самому.
Из корня репозитория:

```bash
mkdir -p build
version="$(git describe --tags --always --dirty)"
commit="$(git rev-parse --short HEAD)"
ldflags="-s -w -X github.com/EXBO-Community/stalcraft-jvm-optimization/internal/buildinfo.Version=${version} -X github.com/EXBO-Community/stalcraft-jvm-optimization/internal/buildinfo.Commit=${commit}"
go build -trimpath -ldflags="${ldflags}" -o build/cli.exe     ./cmd/cli
go build -trimpath -ldflags="${ldflags}" -o build/service.exe ./cmd/service
```

Оба бинарника затем кладутся в одну директорию — установку делает только `cli.exe`, но он ищет `service.exe` рядом с собой.

Проверки локально и в Windows CI запускаются одной командой: `bash scripts/check.sh` (gofmt, go vet, сборка и тесты с race detector). На macOS/Linux выполняются переносимые тесты и Windows cross-build; полный UI и реестр проверяются только на Windows.

Git сохраняет LF для `.go` и `.sh` через `.gitattributes`, в том числе при Windows-checkout с `core.autocrlf=true`. Это необходимо для одинакового результата `gofmt` и запуска Bash-скриптов.
